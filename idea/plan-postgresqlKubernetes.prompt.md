## Plan: PostgreSQL and Kubernetes Readiness

Move the application from its embedded SQLite database to an external PostgreSQL service, and remove process-local state/coordination assumptions before running multiple Kubernetes replicas. Preserve the existing Flask application and file-based document model initially, but make shared file storage an explicit deployment requirement or replace it with object storage.

**Current behavior and findings**
- `app/db.py`: `verbinden()` opens `sqlite3.connect`, registers `NATUERLICH`, sets `sqlite3.Row`, and enables `PRAGMA foreign_keys`; `get_db()`/`close_db()` use request-scoped Flask `g`. `init_db()` applies 22 sequential migrations, versions 1-22, tracked with `PRAGMA user_version`; SQLite DB path is `NK_DATA/nebenkosten.sqlite` (default `./data/nebenkosten.sqlite`).
- `app/core.py`: `db.init_db()` runs during import. `rows()`/`one()` convert SQLite rows into dicts; `exe()` commits each statement and returns `cursor.lastrowid`. `einstellung_setzen()` and an `immobilien.py` upsert use `ON CONFLICT ... excluded`; most SQL uses `?` placeholders. Gunicorn imports `main:app`; multiple workers/pods can concurrently initialize or migrate the same database.
- PostgreSQL-specific query risks: widespread `?` bindings across `auth.py`, `einstellungen.py`, `immobilien.py`, `dokumente.py`, `export.py`, and `vertraege.py`; `lastrowid` and `sqlite3.Row`; `IS NOT ?` (`einstellungen.py`, use null-safe `IS DISTINCT FROM` semantics); custom `COLLATE NATUERLICH` sorting and `COLLATE NOCASE` case-insensitive uniqueness/lookups; SQLite `LIKE` behavior, boolean/null-order expressions, and `substr` date filters. DDL also relies on SQLite `INTEGER PRIMARY KEY` generation and dynamic typing. A DSN/driver swap alone will not work.
- `app/main.py` calls `vertraege.starten()` at import. `app/vertraege.py` starts an in-process daemon thread every six hours unless `NK_ERINNERUNG=aus`. In Kubernetes, every pod/process can send the same reminders. The app writes reminder markers only after all recipient SMTP sends complete, so concurrent runs or partial mail failure can lead to duplicates.
- `app/core.py` has `/health`, which runs `SELECT 1`; there is no separate liveness/readiness endpoint. Docker HEALTHCHECK probes `/health`. Kubernetes must distinguish process liveness from dependency readiness to avoid restarting healthy app processes during a DB outage.
- `app/dateien.py`: documents are stored beneath `DOK_DIR` (`NK_DOKUMENTE`, default `./dokumente`) with relative paths persisted in `dokument`/`ablage`; `dokument_pfad()` resolves them. Photos and logos are in `BILD_DIR = DATA_DIR/bilder`: `profil_<uid>.jpg`, `logo.png`/`logo.jpg`, with logo filename in `einstellung.logo_datei`. Compose mounts named volumes at `/data` and `/dokumente`; `docs/13-betrieb.md` and `README.md` document backup/restore. PostgreSQL migration does not itself require moving these filesystem assets, but multi-replica deployments need shared storage or object storage.
- `app/core.py` `_secret_key()` uses `SECRET_KEY` or creates `DATA_DIR/secret_key` (normally `/data/secret_key`). Flask's default session is a signed client-side cookie, not a DB-backed session; user id, CSRF, pending 2FA, year and form drafts are cookie state. `app/auth.py` password reset/invitation links use the same key. Losing/changing it invalidates sessions and outstanding links. `app/zweifaktor.py` stores TOTP secret/counter and recovery-code hashes in `benutzer`, so preserve them in data migration. `.env.example` does not currently list `SECRET_KEY`; SMTP and `APP_URL` are env-configured, but no DB config exists.
- Compose targets a single app container with named `/data` and `/dokumente` volumes. README describes SQLite and Docker-volume backups. Existing tests use a temporary SQLite DB, assert SQLite file contents, and test SQLite-specific migrations. CI builds/tests the image and checks `/health` plus first-run route, but has no PostgreSQL service, migration concurrency, replica, or readiness test.

**Recommended architecture**
- Preferred app persistence path: introduce PostgreSQL through an explicit database/repository boundary and PostgreSQL-native schema migrations (recommended SQLAlchemy Core/SQLAlchemy connection layer plus Alembic, while retaining the existing business/calculation logic). Avoid trying to preserve SQLite SQL by string replacement. `core.rows/one/exe` are the narrow existing call boundary, but dialect conversion and generated-ID handling still need systematic treatment.
- Keep PostgreSQL as an external managed/service dependency in production; provide a PostgreSQL service only in developer/test Compose and CI. Configure DSN/SSL/pool/connect timeouts through environment variables/secrets, use a least-privilege app role, and run migrations as a one-shot release/init job before app rollout rather than at web-module import.
- Make web replicas stateless with respect to the database and session key. For uploaded documents, either require a shared RWX volume for the first iteration, or prefer S3-compatible/object storage behind a small storage abstraction for true replica portability. Move photo/logo storage with the document storage decision. Set `SECRET_KEY` from a Kubernetes Secret; do not generate a different secret per replica.
- Remove reminder scheduling from `main:app` import. Initially run a single dedicated scheduler/CronJob deployment, guarded by a PostgreSQL advisory lock or durable lease and a database-backed claim/outbox so retries and partial mail failures are controlled. SMTP cannot offer true exactly-once delivery; document and test the selected at-least-once/idempotency behavior. Web pods should have no background scheduler.
- Provide `/live` as process-only and `/ready` as database connectivity (and optionally completed startup/migration readiness); map Kubernetes liveness and readiness probes separately. Keep `/health` temporarily as a compatibility alias if existing installs/monitors depend on it.

**Steps**
1. **Database boundary and schema**: inventory SQL semantics and data types; replace SQLite-specific connection/migration assumptions with the selected PostgreSQL persistence layer. Convert all 22 schema revisions into versioned PostgreSQL migrations, define generated IDs and case-insensitive/natural ordering explicitly, and make migration execution a separate command/job. Preserve the existing transaction/commit semantics intentionally and add rollback/error handling where conversion exposes partial-write risk.
2. **Data migration and cutover**: add a one-time offline SQLite-to-PostgreSQL importer for supported current schema, preserving IDs, nulls, settings, users, and all relational records; reset PostgreSQL sequences after import. Keep file bytes in the selected shared/object store and preserve relative paths. Provide a documented backup, read-only freeze, import, validation, config switch, and rollback procedure; do not silently support dual-write.
3. **Application state and configuration**: define validated DB environment config, pool lifecycle/timeouts, explicit stable session `SECRET_KEY`, and storage configuration. Move migration out of `app/core.py` import. Ensure app start fails clearly on invalid mandatory config while health/readiness accurately report dependency state.
4. **Reminder execution**: separate `vertraege.pruefen()` from scheduling. Add a dedicated scheduler entry point, single-run coordination/claim records, idempotent reminder events/outbox and recovery behavior around SMTP acceptance/marker updates. Configure web deployment to disable all background execution.
5. **Kubernetes/developer operations**: add PostgreSQL-backed Compose and CI profiles; document external DB and storage provisioning, secrets, backup/restore, migration job ordering, replica safety, resources, graceful shutdown, and probes. Add manifests/examples only if the repository's deployment scope expects them; avoid implying Kubernetes manifests alone provision durable Postgres/storage.
6. **Validation and rollout**: run current behavior tests on PostgreSQL, migration/import checks, failure/retry/concurrency tests, and multi-replica checks before rollout. Keep SQLite migration/import tests isolated if SQLite remains as a legacy import format, not a second production runtime.

- `app/core.py` — import-time `db.init_db`, `rows/one/exe`, session-secret generation, and `/health`.
- `app/main.py` — route registration and import-time `vertraege.starten()`.
- `app/vertraege.py` — `pruefen`, `_schleife`, `starten`, and reminder marker updates.

- `docker-compose.yml` and `docker-compose.build.yml` — single-instance volumes and optional environment file.
- `Dockerfile` — one Gunicorn worker/four threads; image HEALTHCHECK to `/health`.
- `.env.example` and `README.md` — current runtime configuration, SQLite storage, and backup instructions.
- `tests/test_app.py`, `tests/test_migration.py`, `tests/test_calc.py` — SQLite-specific end-to-end, migration, and custom collation coverage.
- `.github/workflows/tests.yml` and `.github/workflows/image.yml` — add PostgreSQL service integration and gate publishing on database-backed checks.

**Verification**
1. Run the existing unit/end-to-end suite against PostgreSQL and preserve SQLite only for explicit legacy import/migration coverage.
2. Test every migration from an empty PostgreSQL DB and an imported SQLite DB, including representative collations, case-insensitive login, IDs/sequences, foreign keys, null ordering, and existing schema version 22 data.
3. Test migration job idempotency and two simultaneous app starts; assert app imports/startup do not attempt schema migration.
4. Inject DB connection loss and recovery; verify `/live` stays successful while `/ready` fails and recovers, and verify Kubernetes probe mappings do not cause restart loops.
5. Run at least two web replicas and confirm shared sessions, uploads/downloads, photos/logos, DB writes, and no reminder execution in web pods.
6. Run two scheduler instances concurrently and inject SMTP failure after one recipient; verify claim locking and retry behavior do not silently lose reminders and document duplicate-delivery boundaries.
7. Exercise SQLite import against a production-like backup: compare per-table row counts, foreign-key checks, representative records/settings, ID sequence state, and uploaded-file existence/checksums; rehearse rollback to frozen SQLite backup.
8. CI should run PostgreSQL-backed tests and an integration startup/readiness check using a service container; test the scheduler coordination path separately.

**Decisions and scope**
- PostgreSQL is the only production database after cutover; avoid indefinitely maintaining dual live backends.
- Recommended preferred route is SQLAlchemy Core + Alembic and an explicit importer; exact library/API choice can be finalized before implementation based on appetite for minimizing the SQL rewrite versus long-term migration maintainability.
- Kubernetes statelessness includes DB/session state, not just container filesystem. The app still has uploaded files, photos, and logos; a shared volume is an interim option, object storage is the stronger scaling target.
- Scope excludes changing business calculations, replacing SMTP, or redesigning the UI.
